Date: 2026-11-09 · Size: L · Branch: `sso-sites` (implementation; this document is on `sso-sites-plan`) · Explainer: `tds-website-200925/docs/plans/2026-11-09-passkeys-follow-up-explainer.html` (covers both plans)

**Goal:** make the plugin a good fit for admins who sign in with Google or another SSO provider and are never shown a password, and fix what the first real adoption (the TDS website, 2026-11-09) turned up.

**Architecture:** one new option, `reauthentication: 'password' | 'sign-in-again'`, switches the "your sign-in is too old to add a passkey" path from a password prompt to a "sign in again" action and turns the `reauth` endpoint off. One new server export, `signInVerifiedUser`, lets a host's SSO callback create an ordinary Payload session through the existing `mintSession`, so hosts stop storing random passwords to call `payload.login`. `resetPasskeys`, already the engine behind `payload passkeys:reset`, becomes public for offboarding hooks.

**Tech stack:** Payload CMS `>=3.90 <4`, SimpleWebAuthn, Vitest (unit, int with MongoDB/Postgres/SQLite), Playwright e2e, Changesets.

---

## Objective

On the TDS website, staff sign in only with Google. Three things went wrong there: the plugin asks for a password nobody has seen, five wrong guesses in that box lock the account (and Google sign-in with it), and the site's Google callback has to keep every user's random password in plain text so it can call `payload.login`. The reset command also says "No users user matches …". This release fixes all four without changing anything for password sites.

## User decisions (fixed)

- Scope: every plugin recommendation from the TDS install review (2026-11-09).
- Everything is additive and off by default: password sites see no change. Release as a minor (1.1.0).

## Decisions

1. **`reauthentication` option, default `'password'`.** With `'sign-in-again'`: the `reauth` endpoint isn't registered (404); `register/options` still answers 403 `reauth_required` when the session is older than `freshSessionMinutes`; the client shows a dialog ("Sign in again to add a passkey" + one button) instead of the password prompt. The button calls Payload's logout, then goes to the admin login route with `?redirect=` set to the current admin path.
   Plain: an SSO admin is never shown a password box, so they can't lock themselves out by guessing.
2. **Neutral wording in `'sign-in-again'` mode.** Every default string that says "password" gets a sibling key ending `Sso` (for example `sectionDescriptionSso`: "Sign in with your fingerprint, face or device PIN. Your usual sign-in still works."). The client picks the `Sso` key in that mode. Host overrides of either key keep working.
   Plain: SSO sites get sensible wording without writing their own.
3. **`signInVerifiedUser({ payload, collection, userId, headers? })` → `{ setCookie, user, exp }`, exported from the package's main (server) entry** (overseer: yes, a public export; without it hosts hand-roll `jwtSign` and skip sessions, lockout reset and `beforeLogin`. No extra "intent token" parameter). It builds a request with Payload's exported `createLocalReq`, then calls `mintSession` with no passkey, so it runs exactly what a passkey sign-in runs: session added, failed-login count and lock cleared, `beforeLogin` hooks (which can refuse), `onSignIn` (with `method: 'sso'`), token signed, `afterLogin` hooks. It refuses a collection that isn't configured, and it never checks identity: the README says, in bold, that the caller must have verified the user (an OAuth callback that checked `state` and the provider's response).
   Plain: a site's Google sign-in can create a normal Payload session without keeping any password.
   Note for hosts: the cookie uses the collection's `auth.cookies` settings, and Payload's default is `secure: false`; the README tells hosts to set `secure` in production.
4. **`onSignIn` gets `method: 'passkey' | 'sso'`.** `passkey` stays set only for passkey sign-ins. Additive; existing hooks ignore it.
   Plain: one audit hook can tell the two kinds of sign-in apart.
5. **`resetPasskeys` is exported** with an optional `req` (so a hook's write joins its transaction) and the existing return shape. The README shows an offboarding hook. Trade-off, documented in the README and the JSDoc: when it joins the caller's transaction, `runSessionWrite` (`src/server/sessions.ts:243-252`) rethrows a write conflict instead of retrying, so an admin's save that races the user's token refresh fails and has to be saved again. Without `req` it keeps today's retrying behaviour.
   Plain: a site can remove a leaver's passkeys and sessions from its own admin action, not only from the command line.
6. **The reset message reads "No user in the `<collection>` collection matches `<id or email>`."**
   Plain: fixes "No users user matches".
7. **README "Admins who sign in with SSO" section**: when to use `'sign-in-again'`; `signInVerifiedUser` in an OAuth callback (Next route handler sample, typechecked by `readmeSamples.spec.ts`); offboarding (a `beforeLogin` hook that refuses disabled users covers both SSO and passkeys, plus `resetPasskeys`); overriding wording with a typed `PasskeysTranslations` export; rate-limit hooks may skip `action === 'status'` (anonymous, read-only, on every login-page view).
   Plain: the next SSO site can follow the README instead of rediscovering this.
8. **Phase-2 lock screen honours `reauthentication`.** In `'sign-in-again'` mode, a user with no passkey gets "Sign in again" on the lock box, not a password field (design D11 amended; `docs/plans/2026-11-06-phase-2-lock-screen.md` Task 4 is skipped in that mode).
   Plain: the future lock screen won't reintroduce the password box on SSO sites.

## Contract

`src/types.ts` (additions):

```ts
export type Reauthentication = 'password' | 'sign-in-again'

export type PasskeysPluginOptions = {
  // …existing
  /** How an admin proves it's them when their sign-in is older than freshSessionMinutes. */
  reauthentication?: Reauthentication
}

export type OnSignInArgs = {
  // …existing (collection, passkey?, req, user)
  method: 'passkey' | 'sso'
}

export type SignInVerifiedUserArgs = {
  collection: string
  /** Request headers, for logging and the client IP; optional. */
  headers?: Headers
  payload: Payload
  userId: number | string
}

export type SignInVerifiedUserResult = {
  exp: number
  /** A complete Set-Cookie header value for Payload's auth cookie. */
  setCookie: string
  /** The user as /me returns it. */
  user: Record<string, unknown>
}

export type PasskeysTranslations = Partial<Record<PasskeysTranslationKey, string>>
```

`src/index.ts` (additions): `export { signInVerifiedUser } from './server/signInVerifiedUser.js'`, `export { resetPasskeys } from './server/reset.js'`, and the types above.

Client: `PasskeysProvider` and `PasskeysManagerField` receive `reauthentication` through `clientProps` (set in `src/index.ts` and `src/collections/userFields.ts`).

import { signInVerifiedUser } from '@the-digital-stride/payload-passkeys'

const { setCookie } = await signInVerifiedUser({
