# Release setup: repository and npm settings

The release workflow (`.github/workflows/release.yml`) depends on settings that live outside the repository, in GitHub's and npm's dashboards. Only a maintainer can change them. Work through this list once, before the first release, and again whenever the repository or the npm organisation changes hands.

Plan reference: Task 44 of `docs/plans/2026-11-06-v1-passkey-sign-in.md`; design §10.

## How the workflow is laid out

`release.yml` runs on every push to `main`, in four jobs, so neither the npm OIDC token nor the release App's private key ever meets the repository's dependencies:

1. **`changes`** (`contents: read`, `pull-requests: read`, no secret, no cache): installs with `--ignore-scripts`, runs `pnpm changeset version` (`@changesets/changelog-github` reads PR details through the read-only token), and uploads what it changed as `version.patch`. With no pending changesets the CLI exits 1 with "No unreleased changesets found."; the job treats exactly that as an empty patch, and fails on anything else.
2. **`version`** (the `version-pr` environment, `contents: write`, `pull-requests: write`, no `id-token`): installs nothing. It downloads the patch, mints a token from the release PR App (below), and runs `changesets/action` with `scripts/apply-version-patch.sh` as its version script: the script refuses a patch that touches anything but `package.json`, `CHANGELOG.md`, `.changeset/` markdown files and `pre.json`; that renames, changes a mode, adds a link or creates `pre.json`; that deletes changelog lines or adds changeset lines; or that changes `package.json` beyond `version`. Then it applies it, and the action opens or updates the version PR. With no pending changesets it does nothing and the next job runs.
3. **`build`** (`contents: read`, no `id-token`, no cache): `pnpm install --frozen-lockfile`, `npm audit signatures` (through `scripts/audit-signatures.sh`, which retries only the intermittent `EMISSINGSIGNATUREKEY` lookup failure), unit tests, `pnpm build`, `pnpm pack`, then `node scripts/check-package.mjs` on that tarball. `node scripts/publish.mjs --tarball … --check` asks npm whether the version is there yet (0.0.0 never publishes). Only if it isn't does it upload the tarball and the changelog section as the `release` artifact.
4. **`publish`** (the `release` environment, `id-token: write`, `contents: write` for the tag): no `pnpm install`, no `node_modules`, no cache. It checks out `scripts/` only, installs npm 11.21.1, downloads the artifact (digest-checked), runs `node scripts/publish.mjs --tarball …` (re-checks the tarball's files and manifest, skips a version already on npm, publishes with `--provenance` on `latest`, or `next` for a prerelease), then `gh release create v<version>` on the release commit. Before that it refuses a `v<version>` tag that already exists on another commit.

`test/unit/releaseWorkflow.spec.ts` fails if a change gives the OIDC token to another job, lets the publish job install anything, gives a write permission to a job that installs dependencies, or puts the release App's key in any job but `version` (which installs nothing).

**Accepted (2026-11-07, narrowed 2026-11-08):** `pnpm changeset version` runs dependency code (`@changesets/cli` and the changelog generator from `node_modules`; `--ignore-scripts` stops only install scripts). Since 2026-11-08 it runs in the `changes` job, which has a read-only token and no secret: a compromised dependency there can't push, open a PR or read the release App's key (a hosted runner has passwordless `sudo`, so any secret in a job running dependency code could be read from the runner's memory). The worst it can do is write a bad patch. `apply-version-patch.sh` limits that to the version files, and reading the version PR's diff before merging (Releasing) catches what those files say. It can't publish either: no `id-token` there, and `publish` needs the `release` environment's reviewer. The packages are pinned in the lockfile and held back seven days by `minimumReleaseAge`.

## Releasing

Every release after the first works the same way.

1. Merge pull requests that carry a changeset (`pnpm changeset`). On each push to `main`, the `version` job opens or updates the **chore: release** PR (branch `changeset-release/main`). It bumps `package.json` and writes `CHANGELOG.md`.
2. **Read the release PR.** When its version is the one you want, read its diff (`apply-version-patch.sh` has already held it to the version files, with only `version` changed in `package.json`; what's left to check is that the version and the changelog entries are the ones you expect, since the `changes` job that wrote them runs dependency code, see Accepted above). Its checks run on their own, because the `version` job pushes with the release PR App's token (above). Merging anything else to `main` first updates the PR again and restarts them, so merge the release PR last. If the PR shows "no checks reported", the App isn't set up (or its token step was skipped): the job fell back to its `GITHUB_TOKEN`, whose pushes start no workflow, so start CI by hand with `gh pr close <number> && gh pr reopen <number>` (CI and CodeQL run on the `reopened` event).
3. Merge the release PR once its required checks pass. On that push, `build` finds a version that isn't on npm, so `publish` starts and waits for the `release` environment: open the Release run in the Actions tab, choose **Review deployments**, tick `release` and approve.
4. `publish` publishes the tarball with provenance (`latest`, or `next` for a prerelease) and creates the `v<version>` tag and GitHub release. Check the version on npmjs.com shows provenance for this repository and `release.yml`.

## Checks on the first runs

- [ ] **First `static` run:** compare the package count `npm audit signatures` reports with `pnpm list --depth Infinity --parseable | wc -l` (roughly; pnpm lists the workspace root too). The plan's claim that `npm audit signatures` works on a pnpm-installed tree was checked with npm 10.9.7; a count far below pnpm's means npm isn't seeing the tree, and the check proves less than it says.
- [ ] **First release PR after the release PR App is set up:** the `changes` job uploads a non-empty patch, `version` applies it (its log lists `package.json`, `CHANGELOG.md` and the consumed changesets), the PR is opened by the App's bot, and its checks start on their own. On the merge, `changes` logs "No unreleased changesets found." and passes, and `build` runs.
- [ ] **Whenever Dependabot bumps `@changesets/cli`:** the `changes` job recognises "nothing to version" by the CLI's message "No unreleased changesets found" and its exit code 1. If a new version rewords that or exits 0, the release commit's `changes` job fails (it doesn't do anything unsafe) and nothing publishes until the step in `release.yml` matches. Check the first push to `main` after such a bump.
- [ ] **First Dependabot run:** confirm Dependabot can update this repository with pnpm 11. Its pnpm 11 support is unconfirmed, and pnpm 11 reads its settings (`minimumReleaseAge`, `allowBuilds`, `engineStrict`, `saveExact`) from `pnpm-workspace.yaml`, not `.npmrc`. If the npm ecosystem PRs fail, keep the `github-actions` updates and bump npm dependencies by hand.
